# Промпт: Telegram-бот учёта обращений к дежурному разработчику

## Контекст

Нужно сделать Telegram-бота для учёта обращений первой линии поддержки к дежурному разработчику. Бот фиксирует обращения, отслеживает их статус и исполнителя и даёт просматривать свои и все обращения.

Бот НЕ управляет графиком дежурств: обращение берёт тот разработчик, который нажал кнопку «Взять». Общение по сути обращения идёт вне бота, бот отвечает только за учёт и статусы. Интерфейс пользователя на русском языке.

## Стек

- Python 3.14. Перед началом проверь, что все зависимости поддерживают 3.14 (есть wheels, нет известных несовместимостей). Если что-то не поддерживает, сообщи до реализации, а не понижай версию молча.
- FastAPI, python-telegram-bot v21+ (async).
- PostgreSQL, SQLAlchemy 2.x (async, asyncpg), Alembic.
- pydantic-settings для конфигурации.
- Telegram Mini App: статический фронтенд, который отдаёт FastAPI. **[допущение]** Vanilla JS + Telegram WebApp SDK, без сборки. Если сочтёшь, что нужен фреймворк, предложи и обоснуй до реализации.

## Роли

Роли хранятся в БД: `support` (первая линия), `developer`, `admin`.

- У пользователя не более одной роли (nullable-поле `role` в таблице пользователей). admin имеет все права support и developer, а также управляет ролями, переоткрывает и переназначает обращения.
- Права проверяются на каждый апдейт и API-запрос по текущей роли из БД и не кешируются, поэтому смена роли действует сразу.
- Нельзя сменить роль developer или admin на роль без права быть исполнителем (support или отсутствие роли), пока у пользователя есть обращения в `in_progress` или `waiting_info`. Сначала admin переназначает их. Смена роли блокирует строку пользователя (`FOR UPDATE`), а взятие и переназначение блокируют строку исполнителя (`FOR SHARE`), чтобы проверку нельзя было обойти параллельным взятием.
- Любой пользователь, написавший боту /start, регистрируется без роли и доступа не имеет. Бот сообщает, что нужно обратиться к администратору.
- Первичные админы задаются через env `BOOTSTRAP_ADMIN_IDS` (список Telegram ID) и получают роль при первом /start.
- Админ назначает и меняет роли в Mini App.
- Пользователь идентифицируется по telegram_id. username и имя храним и обновляем при каждом взаимодействии.

## Сущности и статусы

Обращение (ticket):

- номер обращения: целое число, присваивается автоматически на стороне БД (identity-колонка / sequence в PostgreSQL), пользователь его не вводит. В интерфейсе отображается как #123. Номер уникален, не переиспользуется, пропуски допустимы.
- автор, исполнитель (nullable)
- описание (обязательно, до 3000 символов)
- приоритет **[допущение: critical / high / medium / low]**
- id заявки (обязательно, строка до 64 символов) **[допущение: формат не валидируется, только непустота и длина]**
- id арендатора (опционально, строка до 64 символов)
- статус
- `version`: целое число NOT NULL, начальное значение 1. Увеличивается на 1 только при бизнес-изменении: смене статуса, исполнителя или редактируемых данных обращения. Переход статуса вместе со всеми сопутствующими полями (исполнитель, `taken_at`, `closed_at`, `next_reminder_at`) — одна операция: одно увеличение version и одно событие в журнале. Технические записи version НЕ увеличивают: сохранение `message_id` и `post_synced_version`, перенос `next_reminder_at` при срабатывании напоминания. Используется для защиты от устаревших действий и для синхронизации поста.
- `created_at`, `updated_at`, `taken_at`, `closed_at`, `next_reminder_at` (все timestamptz, UTC):
    - `updated_at` обновляется автоматически при любом изменении записи, включая технические (onupdate в SQLAlchemy или триггер в БД; выбери один способ и используй его последовательно для всех таблиц, где есть `updated_at`);
    - `taken_at` хранит начало текущего назначения: ставится при взятии и переназначении, очищается при возврате в `new`;
    - `closed_at` ставится при переходе в любой финальный статус (`resolved`, `rejected`, `duplicate`) и очищается при переоткрытии;
    - `next_reminder_at` описан в разделе «Напоминания».
- `message_id` поста в чате разработчиков (nullable) и `post_synced_version` (NOT NULL, начальное значение 0): версия обращения, из которой отрендерен текущий пост

Статусы: `new`, `in_progress`, `waiting_info`, `resolved`, `rejected`, `duplicate`.

Переходы (реализовать как явную state machine с тестами):

- new → in_progress: кнопка «Взять» (developer, admin). Исполнителем становится нажавший, `taken_at = now()`.
- in_progress ↔ waiting_info: исполнитель или admin.
- in_progress | waiting_info → resolved | rejected | duplicate: исполнитель или admin. Из `new` в финальные статусы перейти нельзя: обращение сначала берут.
- in_progress | waiting_info → new («Отказаться»): исполнитель или admin **[допущение]**. Исполнитель и `taken_at` сбрасываются.
- resolved | rejected | duplicate → new (переоткрытие): только admin, в карточке Mini App. Исполнитель, `taken_at` и `closed_at` сбрасываются.
- Переназначение: только admin, в карточке Mini App, в статусах `in_progress` и `waiting_info`, только на пользователя с ролью developer или admin. Статус не меняется, `taken_at = now()`.

Инварианты проверяются в сервисном слое и CHECK-ограничениями в БД:

- `new` всегда без исполнителя и без `taken_at`;
- `in_progress` и `waiting_info` всегда с исполнителем и `taken_at`;
- `closed_at` заполнен тогда и только тогда, когда статус финальный.

Время до взятия для метрик считается от последнего входа в `new` (создание, отказ или переоткрытие) до взятия. Момент входа берётся из журнала событий.

Права:

- создавать обращения: support, admin
- брать обращения: developer, admin
- остальные действия со взятым обращением: исполнитель и admin; переоткрытие и переназначение: только admin
- Каждая операция бизнес-изменения существующего обращения выполняется одним условным `UPDATE`, который проверяет ожидаемый статус и ожидаемую `version` и увеличивает её: `WHERE id = :id AND version = :expected_version AND status = :expected_status`. Права проверяются в той же транзакции. Кнопки поста и запросы Mini App передают ожидаемую version. Создание обращения (INSERT) и технические записи (синхронизация поста, перенос напоминания, «Восстановить пост») под это правило не подпадают и version не увеличивают.
- При несовпадении операция не выполняется: пользователь получает alert «Обращение изменилось», пост пересинхронизируется. Это защита от конфликтующих и устаревших действий, включая циклы вида in_progress → waiting_info → in_progress. Отдельные ключи идемпотентности операций не вводятся.
- «Взять» атомарно по тому же правилу; при гонке второй нажавший получает alert «Уже взято».
- `callback_data` в Telegram ограничен 64 байтами: используй компактный формат, например `t:<действие>:<id>:<version>`.

Все бизнес-изменения обращения пишутся в журнал `ticket_events` в той же транзакции: тип события (создание, взятие, смена статуса, отказ, переназначение, переоткрытие), кто, когда, старые и новые статус и исполнитель, version после изменения. Технические записи (синхронизация поста, перенос срока напоминания) в журнал не пишутся. В UI журнал пока не показывается, он нужен для аудита и метрик.

## Бот

### Создание обращения (только в личке с ботом)

Пошаговая форма: описание (до 3000 символов) → приоритет (inline-кнопки) → id заявки (до 64 символов) → id арендатора (до 64 символов, можно пропустить кнопкой) → экран подтверждения «Отправить / Отменить». Нужна валидация на каждом шаге (непустота, длина) и команда /cancel в любой момент.

ВАЖНО: приложение работает в Kubernetes в нескольких репликах, и соседние апдейты одного пользователя могут попасть в разные поды. Поэтому форму НЕ реализовывать через ConversationHandler и встроенную персистентность PTB: BasePersistence держит данные в памяти процесса и лишь периодически сбрасывает их в хранилище, с несколькими репликами состояние разъедется. Вместо этого:

- черновик хранится в таблице `ticket_drafts`: UUID-идентификатор (новый для каждого черновика), не более одного активного черновика на пользователя, текущий шаг, заполненные поля, `version`, `prompt_message_id` (nullable), `updated_at`;
- правила версии черновика (то же разграничение, что для обращения):
    - успешное изменение введённых данных или шага выполняется в транзакции под `SELECT ... FOR UPDATE` и увеличивает `version` ровно один раз;
    - отклонённые и устаревшие апдейты (чужой id черновика, устаревшая версия, ответ без нужной привязки) не меняют данные, шаг и `version`;
    - запись `prompt_message_id` — техническая и `version` не увеличивает;
- в `callback_data` кнопок формы вшиваются id черновика и его `version` (в пределах 64 байт, например UUID в компактной кодировке). Нажатие с чужим id или устаревшей версией отклоняется с подсказкой продолжить с актуального шага. Так кнопка от удалённого черновика не может подтвердить новый;
- текстовый ответ привязан к конкретному вопросу формы. Вопрос шага, ждущего текст, отправляется с `ForceReply`, и его message_id сохраняется в `prompt_message_id`. На сервере ответ принимается, только если `reply_to_message.message_id` совпадает с `prompt_message_id` черновика. ForceReply лишь помогает в интерфейсе и серверной проверки не заменяет;
- переход к следующему шагу: в одной транзакции сохранить ответ, перейти на следующий шаг, обнулить `prompt_message_id` и увеличить `version`. После коммита отправить вопрос нового шага;
- результат отправки любого вопроса (следующего шага или повторного показа) сохраняется условным обновлением: `UPDATE ... SET prompt_message_id = :msg_id WHERE id = :draft_id AND version = :version AND step = :step`, где draft_id, version и step — те, для которых вопрос был сформирован. Если черновик за это время изменился или удалён, `prompt_message_id` не перезаписывается, а ответы на такой вопрос будут отклонены. Транзакция во время запроса к Telegram открытой не держится. Если отправка не удалась, `prompt_message_id` остаётся прежним или пустым;
- сообщение без нужной привязки (не reply, reply на другой вопрос, пустой `prompt_message_id`) не меняет данные, шаг и `version`: бот заново задаёт текущий вопрос и сохраняет его message_id по правилу выше. Так повторно отправленный после сбоя ответ не попадёт в следующее поле. /new → «Продолжить» работает так же;
- «Отправить» в одной транзакции создаёт обращение и удаляет черновик, поэтому повторное нажатие ничего не создаст. Пост публикуется после коммита через синхронизацию поста (см. ниже), так что сбой публикации не теряет обращение;
- черновики старше TTL из конфига **[допущение: 24 ч]** удаляются, /new при существующем черновике предлагает продолжить или начать заново.

### Публикация в чат разработчиков

Для каждого обращения в чате `DEV_CHAT_ID` есть пост: номер, данные обращения, автор, статус, исполнитель и кнопки, доступные в текущем статусе («Взять» для `new`; «В ожидании информации», «В работу», «Решено», «Отклонено», «Дубль», «Отказаться» для взятого). Кнопки видят все, права проверяются на сервере, при отказе показывается callback alert. Автору в личку уведомления НЕ отправляются.

Текст поста гарантированно укладывается в лимит Telegram 4096 символов: при необходимости описание обрезается с «…», полный текст доступен в карточке Mini App.

Источник истины — БД, пост лишь её отображение. Первая публикация и все последующие правки выполняются одной процедурой синхронизации поста:

1. Взять session-level advisory lock PostgreSQL (`pg_advisory_lock` / `pg_try_advisory_lock`) по id обращения на одном выделенном физическом соединении, с таймаутом. Это сериализует работу с одним постом между репликами; asyncio.Lock внутри процесса недостаточно. Блокировка снимается через `pg_advisory_unlock` в `finally`, в том числе при ошибке, таймауте и отмене задачи. Возврат соединения в пул снятием блокировки не считается: она живёт до явного снятия или конца сессии. Если снять блокировку не удалось, соединение закрывается, а не возвращается в пул.
2. Под блокировкой прочитать актуальное состояние обращения из БД и отрендерить пост из него, запомнив version, из которой он отрендерен. Никогда не отправлять повторно ранее подготовленный текст.
3. Если `message_id` пуст, отправить новый пост, иначе отредактировать существующий. Если пост удалён или недоступен для редактирования, опубликовать новый.
4. Одной транзакцией сохранить результат: `post_synced_version` = отрендеренная version и, для нового поста, его `message_id`. Сохраняется именно отрендеренная version, а не текущая: если бизнес-состояние за время отправки изменилось, фоновая задача увидит отставание и синхронизирует ещё раз. Эта запись version не увеличивает.
5. Снять блокировку.

Синхронизация вызывается сразу после коммита создания или бизнес-изменения обращения. Фоновая задача в каждой реплике периодически находит обращения с пустым `message_id` или `post_synced_version < version` и синхронизирует их (через `pg_try_advisory_lock`, занятые пропускает). Так созданное обращение без поста будет опубликовано без участия пользователя, а новое обращение никогда не создаётся повторно.

Ограничение: если пост удалили вручную уже после успешной синхронизации, фоновая задача этого не заметит, ведь `post_synced_version == version`. Пост восстановится при следующей синхронизации этого обращения или вручную: в карточке Mini App у admin есть действие «Восстановить пост», которое принудительно публикует новый пост и заменяет `message_id`. Периодическая проверка всех постов не требуется.

Ошибки Telegram ретраятся с backoff с учётом `retry_after` при 429; ошибка «message is not modified» считается успехом. Если результат отправки нового поста неизвестен (например, таймаут), допускается редкий дубль поста: в БД сохраняется message_id последнего успешно отправленного.

### Напоминания

Если обращение в статусе `new` не взято дольше интервала, зависящего от приоритета, бот пишет напоминание в чат разработчиков ответом (reply) на пост. Напоминание повторяется с тем же интервалом, пока обращение не возьмут. Интервалы задаются в конфиге **[допущение: critical 10 мин, high 30 мин, medium 2 ч, low 8 ч]**.

Семантика доставки: не более одной попытки отправки на каждый срок. Потеря напоминания при сбое допустима, следующее придёт через интервал. Правила расписания:

- при создании обращения и при любом входе в `new` (отказ, переоткрытие) в той же транзакции ставится `next_reminder_at = now() + интервал приоритета`;
- при выходе из `new` поле очищается в той же транзакции;
- после срабатывания следующий срок считается от текущего времени: `next_reminder_at = now() + интервал`. Так после простоя не возникает серии догоняющих напоминаний.

Алгоритм:

1. Фоновая задача в каждой реплике с интервалом опроса из конфига в одной транзакции выбирает обращения со `status = 'new'` и `next_reminder_at <= now()` через `SELECT ... FOR UPDATE SKIP LOCKED`, сдвигает `next_reminder_at` и коммитит.
2. Только после коммита отправляются напоминания ответом на пост (если поста ещё нет, то без reply). Ошибка отправки логируется и уходит в Sentry, повторной отправки нет.
3. Блокировка снимается при коммите, до отправки, поэтому одно уже подготовленное напоминание может прийти после того, как обращение взяли. Это явно допустимо, дополнительная защита не нужна.

In-memory JobQueue PTB не использовать: SKIP LOCKED исключает двойную обработку между репликами только при хранении расписания в БД.

### Прочие команды

/start, /help, /new (создать обращение), /cancel, кнопка меню для открытия Mini App. Учти, что web_app-кнопки работают только в личных чатах.

## Mini App

- Авторизация: валидация `initData` по HMAC-SHA256 с ключом от токена бота, проверка свежести `auth_date` (порог в конфиге). Пользователь определяется по telegram_id, доступ даётся по роли из БД.
- Экраны:
    - «Мои обращения»: для support созданные мной, для developer назначенные мне (admin видит обе вкладки)
    - «Все обращения»
    - фильтры по статусу и приоритету, пагинация, сортировка по дате (новые сверху)
    - карточка обращения: полное описание и все поля. Статусы меняются через бота, кроме действий admin ниже
    - действия admin в карточке: переоткрыть закрытое обращение; переназначить взятое обращение на пользователя с ролью developer или admin (запрос передаёт ожидаемую version, после успеха пост синхронизируется); «Восстановить пост» (принудительная публикация нового поста, version не меняется)
    - управление ролями (только admin): список пользователей, назначение и смена роли. При попытке снять право быть исполнителем у пользователя с активными обращениями API возвращает ошибку со списком этих обращений
- Поддержать тему Telegram (светлая и тёмная) через параметры WebApp.

## FastAPI

- `POST /telegram/webhook`: приём апдейтов с проверкой заголовка `X-Telegram-Bot-Api-Secret-Token`. PTB Application без Updater, жизненный цикл PTB привязан к lifespan FastAPI. Апдейт обрабатывается синхронно внутри запроса (`await application.process_update(...)`) с таймаутом из конфига. Ошибки обработки логируются и уходят в Sentry, но ответ всё равно 200, чтобы Telegram не повторял заведомо сбойный апдейт.
- Дедупликация апдейтов и граница транзакции: запись `update_id` в таблицу `processed_updates` (уникальный ключ, `INSERT ... ON CONFLICT DO NOTHING`) выполняется и коммитится отдельной короткой транзакцией ДО бизнес-обработки. Бизнес-обработка идёт в своих транзакциях, и её ошибка не откатывает запись о дедупликации. Если запись уже была, апдейт пропускается.
- Итоговая семантика: не более одной попытки обработки каждого апдейта. Последствия сбоя восстанавливаются так: пользователь повторяет действие (форма и кнопки защищены version), а созданные обращения без поста публикует фоновая синхронизация. Записи `processed_updates` старше 48 часов удаляются. Тот же механизм работает в режиме polling.
- Защиту от конфликтующих действий обеспечивает проверка version (см. раздел «Права»); дедупликация её не заменяет.
- `GET /health/live`, `GET /health/ready` (ready проверяет соединение с БД) на основном порту.
- REST API для Mini App под `/api/...`
- статика Mini App
- Для локальной разработки поддержать `BOT_MODE=polling`, чтобы не нужен был публичный HTTPS. В production работает `webhook`.

## Конфигурация

pydantic-settings: переменные окружения с фолбэком на локальный `.env`. Приложить `.env.example` со всеми переменными и комментариями. Секретов в репозитории быть не должно. В production секреты приходят из внешнего пайплайна как env-переменные.

## Логирование

Структурированные JSON-логи в stdout, пригодные для OpenSearch, с tagged logging: контекстные теги прокидываются через contextvars и попадают во все записи в рамках запроса или апдейта (request_id, update_id, telegram_user_id, ticket_id, component). **[допущение: structlog]**. Уровень логирования и формат (json / человекочитаемый для dev) задаются в конфиге.

## Мониторинг

- Sentry: sentry-sdk с интеграциями FastAPI и SQLAlchemy. Ошибки в хендлерах PTB ловить через error handler и отправлять в Sentry с тегами. DSN опционален: если он не задан, Sentry отключён.
- Prometheus. В каждом pod работает один uvicorn-процесс, масштабирование только числом реплик, поэтому multiprocess-режим prometheus_client не нужен, используется стандартный registry.
- `/metrics` отдаётся на отдельном порту (`METRICS_PORT`), а не на основном HTTP-порту, чтобы метрики не попадали наружу через ingress.
- Middleware собирает HTTP-метрики: число запросов, latency, коды ответов. В label маршрута пишется шаблон пути, а не фактический URL, чтобы не раздувать кардинальность.
- Счётчики и гистограммы считаются в процессе и суммируются по подам через `sum()`: созданные обращения по приоритету, переходы статусов, время до взятия, обработанные и отброшенные как дубли апдейты, отправленные напоминания, ошибки.
- Gauge «открытые обращения по статусу» вычисляется запросом к БД при скрейпе (custom collector). Каждая реплика отдаёт одинаковое значение, поэтому агрегировать его нужно через `max()`, а не `sum()`. Это правило описать в README.

## Docker и локальная среда

- Один multi-stage Dockerfile с таргетами:
    - `dev`: dev-зависимости, hot reload
    - `test`: тестовые зависимости, по умолчанию запускает pytest
    - `prod`: минимальный образ, non-root пользователь, без dev-зависимостей; запускает ровно один uvicorn-процесс (без `--workers` и без gunicorn) и открывает основной порт и порт метрик
- `docker-compose.yml` для локальной разработки: app (target dev, `BOT_MODE=polling`) и PostgreSQL с volume. Отдельный compose-профиль или файл для прогона тестов.
- Миграции Alembic запускаются отдельной командой (в k8s как отдельный job), не при старте приложения. Для dev в compose допустим автозапуск.
- CI/CD и k8s-манифесты НЕ входят в задачу. HTTPS настраивают администраторы инфраструктуры.

## Качество

- ruff (lint + format), mypy на основном коде.
- pytest + pytest-asyncio, тесты на реальном PostgreSQL из compose. Обязательно покрыть:
    - state machine, права и инварианты: admin как developer, запрет перехода из `new` в финальные статусы, переоткрытие и переназначение только admin;
    - version: один переход — одно увеличение; синхронизация поста и перенос напоминания version не меняют и не делают кнопки устаревшими;
    - атомарность «Взять» и проверку version, включая старую кнопку после цикла in_progress → waiting_info → in_progress;
    - синхронизацию поста: после успешной синхронизации обращение не выбирается повторно; конкурентные правки не возвращают устаревший статус; изменение во время отправки приводит к повторной синхронизации; обращение без поста публикуется фоновой задачей; advisory lock снимается при ошибке и отмене; рендер укладывается в 4096 символов;
    - дедупликацию апдейтов и то, что ошибка обработки не откатывает запись в `processed_updates`;
    - черновик: конкурентные апдейты, кнопки от удалённого черновика, повторно отправленный после сбоя ответ не попадает в следующее поле, сообщение не в ответ на текущий вопрос не меняет данные, шаг и version черновика, запоздавшая отправка вопроса не перезаписывает prompt_message_id следующего шага;
    - напоминания: расписание при входе в `new` и выходе из него, отсутствие догоняющих серий, отсутствие дублей при конкурентных воркерах;
    - запрет смены роли при активных обращениях;
    - валидацию initData и API Mini App.
- README: локальный запуск, переменные окружения, миграции, сборка образов, регистрация webhook и Mini App в BotFather, правила агрегации метрик.

## Порядок работы

1. Сначала предложи структуру проекта, схему БД и план реализации по этапам. Дождись подтверждения.
2. Реализуй по этапам: каркас и конфиг → модели и миграции → state machine и сервисный слой → синхронизация поста → бот (форма, кнопки) → напоминания → API и Mini App → логирование и мониторинг → Docker → README.
3. Бизнес-логика живёт в сервисном слое, независимом от Telegram и HTTP. Хендлеры бота и эндпоинты API остаются тонкими.
4. При неоднозначностях спрашивай, а не додумывай молча.
